## 实验目标

课上讲了共识与一致性。区块链把这些问题放到了最不友好的环境里：节点互不信任、随时加入退出、网络会分区，谁都可以发区块。比特币和以太坊（2022 年以前）用**工作量证明（PoW）**和**最重链规则**在这种环境下达成一致，代价是只有**最终一致性**：一笔"已确认"的交易，可能因为链重组（reorg）被撤销。

本实验分两步：

1. **亲手实现一条 PoW 区块链的核心**：挖矿、难度调整、区块头验证、区块的执行与验证、交易池、分叉选择、链重组、区块传播与同步。框架提供了单笔交易的 EVM 执行（go-ethereum 的库）、P2P 网络和以太坊 JSON-RPC，所以你写完的链能直接运行 Solidity 智能合约，web3.py、Foundry 都能连上。
2. **在你自己的链上搭建一个小型 DeFi 经济，并让 AI Agent 在里面交易**：去中心化交易所（AMM）、借贷、预言机、清算；脚本机器人和 LLM 驱动的交易 Agent 在其中博弈。你要设计自己的 Agent，并围绕开放问题进行实验。

## 二、Part 1：实现 PoW 区块链（50 分）

### 2.1 背景：一条 PoW 链是怎么工作的

**账户与交易。** 和以太坊一样，状态是"地址 → 余额、nonce、合约代码和存储"。交易由私钥签名，带一个递增的 nonce（同一账户的第 n 笔交易，nonce = n），所以同一笔交易不能被执行两次，同一个 nonce 只能被用一次。交易还声明它最多用多少 gas（`gas`）、每单位 gas 最多付多少（fee cap）以及其中给矿工的小费（tip）。本链的 base fee 恒为 0，所以手续费 = 实际用掉的 gas × tip，全部归矿工。

**执行。** 一笔交易在某个状态上执行（EVM，框架的 `applyTx`），得到新状态和一张**回执**（receipt：成功还是失败、用了多少 gas、产生了哪些事件日志）。要区分两种"失败"：
- **非法**交易：nonce 不是账户的下一个、余额付不起 gas × fee cap + 转账金额、区块里剩下的 gas 装不下它……它根本不能出现在区块里；
- **执行失败**（revert，比如合约里 `require` 不满足、gas 用完）：它是合法的交易，照样上链、照样扣手续费、nonce 照样加一，只是它对状态的其他修改被撤销，回执的 `status` 为 0。

**区块。** 区块头记录父块哈希、高度、时间戳、难度、矿工地址（coinbase），以及对执行结果的承诺：状态根（执行完这个块之后整个世界状态的 Merkle 根）、交易根、回执根、日志布隆过滤器、用掉的 gas。执行一个块 = 依次执行其中的交易，再给 coinbase 发出块奖励（2 ETH）。任何节点拿到区块都会**自己重新执行一遍**，结果对不上就拒绝。所以矿工可以选择打包哪些交易、按什么顺序，但不能伪造执行结果，也不能凭空给自己加钱。

**交易池。** 用户把交易发给任意一个节点，节点验证后放进**交易池**（mempool）并转发给其他节点，谁挖下一个块谁就从自己的池里挑交易打包。池里的交易按账户、按 nonce 排队：nonce 连续的部分可以马上执行（pending），中间缺了 nonce 的要等（queued）。矿工按小费从高到低打包，所以想快点上链就多付小费；同一个 nonce 再发一笔小费更高的交易，可以**替换**掉池里那笔（加速或取消交易都靠这个）。

**工作量证明。** 出一个块要找到一个 nonce，使 `hash(区块头, nonce) ≤ 2^256 / 难度`。找到的期望尝试次数等于难度，只能靠暴力尝试；验证只要算一次哈希。全网算力是 H 次/秒时，平均每 难度/H 秒出一个块，出块间隔服从指数分布（所以偶尔会等 10 秒以上，这不是 bug）。

**难度调整。** 难度跟着出块速度自动调：块来得太快就调高，太慢就调低，让平均出块间隔接近目标值（本实验 2 秒；由于时间戳只精确到秒，实际稳定在 2.5 秒左右）。

**分叉与最重链。** 两个矿工几乎同时出块，或者网络分区时两边各自出块，就会产生分叉。节点把所有合法区块都存下来，形成一棵以创世块为根的树，并选出**总难度（从创世块到它的难度之和，即"累计工作量"）最大**的叶子作为链头。从创世块到链头的路径就是**规范链（canonical chain）**。

```
                    ┌── A3 ── A4              (TD = 1000+...+A4)
genesis ── 1 ── 2 ──┤
                    └── B3 ── B4 ── B5        (B 分支更重: 规范链)
```

**链重组（reorg）。** 当另一个分支变得更重时，规范链切换过去：A3、A4 不再是规范块（但还存着），B3–B5 成为规范块。A 分支上那些不在 B 分支上的交易要放回交易池，等待重新打包。对用户来说，这意味着"我的交易本来在块 A3 里，现在不在了"。这就是 PoW 只提供**概率性终局**的原因：一笔交易上面压的块越多，被重组掉的概率越小，但永远不是零。

**为什么是"最重"而不是"最长"。** 如果按长度选，攻击者可以用很低的难度造一条很长的链（难度会随着时间戳自动降低）。按总工作量选，伪造一条更重的链需要投入比诚实矿工更多的算力，这才是 PoW 安全性的来源。两条链一样重时，**保留先看到的那一条**（first seen），直到下一个块打破平局。

**传播与同步。** 新块被广播给对等节点，每个节点接受后再转发给自己的对等节点（中继），这样不需要两两相连。收到一个父块未知的块，说明漏了中间的块，向发送者要。但广播会丢（节点宕机、网络分区），所以每个节点还要**定期询问**对等节点的链头，发现更重的就把链拉过来，这样分区愈合后即使没人再出块，节点也能自己重新一致。

#### 任务 1：PoW 封印（`pow.go`）

先读 SPEC.md 的"封印"一节。`SealHash` 是区块头去掉 `Nonce` 和 `MixDigest` 之后的 Keccak256 哈希；`PowHash(sealHash, nonce)` 是 `Keccak256(sealHash ‖ nonce 的 8 字节大端序)`；合法的封印要求 `MixDigest == PowHash` 且 `PowHash ≤ 2^256/难度`。`Seal` 就是一个循环：从随机 nonce 开始逐个尝试，每试 `sealBatch` 个调用一次 `throttle.Wait`（限制算力，同时检查是否该停下）。

- SPEC.md 和 `TestPowSealHashVector` / `TestPowHashVector` 给出了具体的测试向量：你的实现必须**逐字节**一致，否则你的节点和别人（以及评分用的参考实现）的节点互相不认对方的块。
- 不要修改传进来的区块头（用 `types.CopyHeader`）。难度为 nil 或 ≤ 0 时返回错误，不要 panic。

#### 任务 2：难度与区块头验证（`consensus.go`）

`CalcDifficulty` 是以太坊 Homestead 的难度规则（EIP-2），公式在注释和 SPEC.md 里。`VerifyHeader` 按顺序检查 10 条规则，每条违反时返回包装了对应错误的 error（测试用 `errors.Is` 判断），例如 `fmt.Errorf("%w: got %d, want %d", ErrInvalidGasLimit, a, b)`。

- 注意无符号整数：`time - parent.Time` 在 `time < parent.Time` 时会下溢成一个巨大的数。
- 第 3 条规则（时间戳不能比本地时钟超前太多）用传进来的 `now`，不要自己调 `time.Now()`。为什么需要这条规则？如果矿工可以随意把时间戳写到未来，难度调整会被怎样操纵。
- 先做便宜的检查，最后才验证封印（`VerifySeal`）。

#### 任务 3：执行与验证区块（`process.go`）

两个函数，用的是同一套执行规则：

- `build`（矿工造块）：在父块的状态上依次执行候选交易，**非法的跳过**，其余照常执行（一笔交易装不下了，后面更小的交易仍然可以试）；然后给 coinbase 发出块奖励，填好区块头里依赖执行结果的字段（状态根、gas 用量、交易根、回执根、布隆过滤器）。它不写状态数据库，因为这个块插入时还会被 `process` 真正执行一次。
- `process`（验证者）：在父块的状态上**严格地**重新执行收到的块：区块体必须和区块头一致（交易根对得上，没有叔块），任何一笔交易非法，整个块就非法；执行完后比较 gas 用量、布隆过滤器、回执根、状态根，全对才提交新状态（`commitState`）并返回回执。任何拒绝的理由都返回包装了 `ErrInvalidBlock` 的错误。

go-ethereum 的具体调用都包在 `executor.go` 的辅助函数里（`openState`、`newGasPool`、`applyTx`、`payReward`、`stateRoot`、`commitState`、`txsRoot`、`receiptsRoot`、`logsBloom`、`assemble`），你要写的是区块这一层的逻辑。`framework_test.go` 里的 `labEVM.block` 演示了 `applyTx` 和 `commitState` 怎么用（它只执行交易，不发奖励、不检查承诺）。

- `build` 和 `process` 最好共用一个执行循环（带一个 strict 参数）：矿工算出来的区块头和验证者算出来的必须一模一样。
- 想一想：`process` 遇到一笔非法交易时，为什么不能像 `build` 那样跳过它？（提示：跳过之后的执行结果，和一个根本没有这笔交易的块完全一样，但交易根说它在块里。）
- 出块奖励在所有交易**之后**发：矿工不能在自己正在挖的块里花这个块的奖励。
- `TestExecStateRootVector` 固定了一个块的状态根：所有人的实现都必须得到同一个值，否则你的节点和别人的节点互相不认对方的块。

#### 任务 4：交易池（`txpool.go`）

`TxPool` 的内部结构由你设计（注释里有提示）；对外的方法和规则是固定的，框架的 RPC、P2P、矿工和 `setHead` 都靠它们：

- `Add`：先做与状态无关的检查（`ValidateTx`：类型、链 ID、签名、gas 上限、内在 gas、fee cap ≥ tip），再对照链头状态检查 nonce（不能小于账户的 nonce）和余额（付得起 gas × fee cap + 转账金额）。同一账户同一 nonce 已经有一笔时，新交易的 tip **严格更高**才替换，否则返回 `ErrReplaceUnderpriced`；池满（`MaxPoolTxs`）返回 `ErrPoolFull`。nonce 有空缺没关系，先排队。已经在池里的交易返回 `(false, nil)`。
- `Pending`：按矿工应该尝试的顺序返回可以执行的交易：每个账户内部按 nonce 连续取；账户之间每次取"下一笔"小费最高的那个账户，小费相同的先到先得。这是矿工的策略而不是共识规则，但测试和 Part 2 的实验（比如竞价、抢跑）都依赖这个顺序。
- `PendingNonce`、`Content`：钱包的 `eth_getTransactionCount(addr, "pending")` 和 `txpool_content`。
- `reset(st, dropped)`：链头每次变化时 `setHead` 都会调用它。先把重组掉的交易按 `Add` 的规则（但对照新状态）放回去，再删掉新链已经用掉 nonce 的交易；返回放回去的那些（节点会重新广播它们）。

注意：
- 这些方法会被 RPC、P2P、矿工、`setHead` 从不同的 goroutine 同时调用，数据结构要用锁保护；但持有锁时不要再调用会回到池里的函数。用 `go test -race ./chain` 检查。
- `Pending` 可以用一个以"各账户下一笔交易"为元素的堆（`container/heap`）来实现上面的顺序。

#### 任务 5：插入区块、分叉选择、链重组（`blockchain.go`）

这是 Part 1 的核心，也是隐藏测试最多的地方。`insertBlock` 的步骤在注释里写得很清楚：已知 → 父块未知 → 验证区块头 → 执行（`processBlock`）→ 存储（`writeBlock`，总难度 = 父块总难度 + 本块难度）→ 分叉选择。新块比当前链头重时调用 `reorg`。

`reorg(oldHead, newHead)` 要做四件事：找到两个链头的**公共祖先**；把从祖先到新链头的每个块写进规范链索引（`writeCanonical`）；把高于新链头、原来是规范块的高度删掉（`deleteCanonical`）；把旧分支上、新分支上没有的交易交给 `setHead`（它会调用你在任务 4 写的 `reset` 把它们放回交易池）。

- 最常见的情况是 newHead 就是 oldHead 的子块，这时 reorg 退化成"写一个规范块 + setHead"。但你的代码必须也能处理：新链头在另一个分支上、新链比旧链**短**（但更重）、分叉点很深（几十个块）。动手前在纸上画一画这几种情况。
- 平局（总难度相等）不切换。
- 非法的块不能被存储，不能改变链头。
- `insertBlock` 运行时已经持有 `bc.insertMu`，不能在里面调用 `InsertBlock`/`InsertChain`（会死锁；测试会检测到并提示）。`chain.go` 里的读取函数（`GetBlock`、`GetTd` 等）可以随便调用。

#### 任务 6：矿工（`miner.go`）

`mine` 在给定父块上构造一个块（时间戳、难度、coinbase；交易来自 `pool.Pending()`，`BuildBlock` 会执行它们并填好其余字段），封印、插入、广播。`loop` 不断调用 `mine`，并在**链头变化时立刻取消**当前的挖矿（订阅 `bc.SubscribeHead()`），每 `recommit` 秒也重新开始一次以便打包新交易。

- 时间戳取本地时钟（`m.bc.Now()`，测试会替换时钟），但至少是父块时间 + 1；如果这样算出来的时间戳超出了 MaxFutureTime，就等，不要造一个自己都不接受的块。
- 为什么链头变了必须马上放弃？如果不放弃会发生什么？

#### 任务 7：传播与同步（`sync.go`）

`HandleBlock` 处理对等节点推送来的块：已知的忽略（这是中继终止的条件，否则块会在节点之间无限转发）；父块未知的向发送者要祖先（`fetchChain`）；合法的新块转发给除发送者外的所有对等节点；非法的丢弃。`fetchChain` 用 `RequestAncestors` 从某个块往回要，一次最多 `MaxAncestors` 个，直到接上本地已有的块，然后从旧到新插入。`SyncOnce` 询问所有对等节点的链头，从总难度最大的那个拉链；拉失败了就试下一个。框架会每秒调用一次 `SyncOnce`，节点启动时也会先调用一次。

- 不要相信对等节点：它报告的总难度只是个提示，它发来的块可能不连续、可能是错的。检查后再插入，插入时 `InsertBlock` 会验证一切。
- 单元测试用的是假网络（`labFakeNet`），没有时序问题；通过之后再跑 `go test ./tests -v`，那是真实的多进程网络。

### 2.3 调试建议

- **先跑单元测试，再跑多节点测试**，最后用 devnet 手动试。多节点测试失败时，先看它打印的节点日志。框架只打印 `REORG ...`（每次重组）和下面那条 WARNING；**你自己的代码应该在关键处打日志**（用 `bc.log`、`m.log`、`h.log`）：挖出一个块（高度、哈希、状态）、拒绝一个块（原因）、向谁要了多少个祖先。日志写得好，多节点的问题往往一眼就能看出来。
- 在 devnet 里重现问题：`go run ./cmd/devnet -mine=false`，然后用 `partition`、`mine`、`heal`、`status`、`chain`、`reorgs` 一步一步操作，观察每个节点的状态。`curl http://127.0.0.1:28001/admin/blocks` 能看到节点存的整棵区块树。
- 节点状态不一致时，比较 `/admin/chain` 的输出：从哪个高度开始不一样？那个高度上两边的块是什么？
- 看到 `WARNING: setHead(...): that block is not in the canonical index` 说明你先调用了 `setHead` 再更新规范链索引，顺序反了。
- `processBlock rejects the block that BuildBlock made` 说明你的 `build` 和 `process` 执行规则不一样（奖励、gas、跳过了哪些交易）：两边应该共用同一个执行循环。
- 交易发出去却一直不上链：`txpool_content`（见第六节）看它在 pending 还是 queued；`chain n1 5` 看最近的块里有几笔交易。
- 用 `go test -race ./chain` 检查数据竞争。

## 三、Part 2：链上 DeFi 与 AI 交易 Agent（40 分）

Part 1 让你从内部理解一条链；Part 2 让你站在链的用户一侧，看清楚链上的经济系统怎么运作、会怎样出问题，以及一个 AI Agent 在这里能做什么、会犯什么错。

注 2：类似注 1，如下是一条可能的 Part 2 路线，你也可以选择自行研究和设计，Part 2 是开放的，充分鼓励有趣的想法，但至少应当具备相当的工作量。如果选择自行设计，需要额外提交一份书面提案，不超过一页，描述你们的想法和工作，并且应当在验收时向助教完整阐述。

### 3.1 背景：为什么研究"链上 + Agent"

**DeFi（去中心化金融）**把交易所、借贷、清算这些金融功能写成智能合约，部署在链上。规则完全公开、由代码执行，任何人都能参与：没有开户，也没有营业时间。但它也带来了传统金融里少见的问题：

- **价格从哪来？** 链上借贷协议需要知道抵押品值多少钱，这个价格由**预言机（oracle）**提供。预言机报价滞后，或者干脆读 AMM 的即时价格，都可能被操纵或引发错误清算。
- **清算会连锁。** 价格下跌 → 抵押不足的仓位被清算 → 清算人把没收的抵押品卖进市场 → 价格进一步下跌 → 更多仓位被清算。
- **交易顺序是可以买卖的。** 矿工按小费排序打包交易，交易在被打包前对所有人可见（交易池是公开的），于是有了抢跑（front-running）和三明治攻击，即所谓 **MEV**。
- **"已确认"不等于"已终局"。** 你在 Part 1 里亲手实现的链重组，意味着一笔已经有回执的交易可能被撤销。

**AI Agent** 正在开始自主地读行情、做决策、签名发交易。这带来了新的问题：大模型会不会因为相似的训练数据和提示词而**同向交易**，放大波动？它能不能理解清算风险和确认数？链上的数据任何人都能写（代币名称、事件内容），如果直接塞进提示词，会不会被**提示词注入**？模型"幻觉"出一笔错误的交易时，谁来兜底？

这些问题在真实的链上做实验既昂贵又危险。本实验给你一个完全可控的沙盒：你自己的链、一套完整的 DeFi 合约、一群行为各异的机器人，可以随意调网络、调市场、调参与者，反复实验。DeFi 的基础知识（AMM 公式、借贷与清算、预言机、MEV）见 [DEFI.md](DEFI.md)，**建议先读一遍**；写 Agent 的完整接口见 [AGENTS.md](AGENTS.md)。

### 3.2 仿真器：一个小型 DeFi 经济

`cmd/sim` 会启动一个 PoW devnet（用你 Part 1 写的节点），部署合约，然后让一群 Agent 交易一段时间：

| 组成 | 说明 |
|---|---|
| 代币 | USD 和 WETH（两个 ERC-20） |
| AMM | 恒定乘积做市商（Uniswap V2 的核心：`x·y = k`，手续费 0.3%），初始 500 WETH / 100 万 USD，价格 2000 |
| 借贷市场 | 存 WETH 借 USD：最多借抵押品价值的 75%；债务超过 80% 时可被清算，清算人代还最多一半债务、拿走等值的抵押品外加 5% 奖励 |
| 预言机 | Feed：报价人每秒把交易所价格写上链（像 Chainlink）；Spot：直接读 AMM 的即时价格（可被操纵，`-spot-oracle` 让借贷市场用它） |
| 交易所 | 链下的"真实市场"（想象成币安），价格做随机游走，并按设定的时刻发生暴跌（默认 25 秒时开始、20 秒内跌 30%） |
| 内置 Agent | 套利者（把 AMM 价格拉回交易所价格，并在交易所对冲）、清算人、噪声交易者、几个从不调仓的杠杆借款人、报价人；可选：内置 LLM 交易者（`-llm N`） |
| 你的 Agent | 任何语言写的程序，仿真器把它作为子进程启动，给它一个有钱的账户和全部合约地址（`-agent "名字=命令"`） |

```bash
go run ./cmd/sim                                     # 默认场景，60 秒，最后打印报告
go run ./cmd/sim -out results/run1                   # 同时把数据写进 results/run1/
go run ./cmd/sim -agent "me=python3 pysdk/examples/momentum.py"            # 加入你的 Agent
go run ./cmd/mockllm &                                                      # 离线假模型
go run ./cmd/sim -agent "llm=python3 pysdk/examples/llm_trader.py"         # LLM Agent
go run ./cmd/sim -miners 4 -delay 800ms -jitter 800ms -confirmations 3     # 慢网络：频繁分叉与重组
```

常用参数（`go run ./cmd/sim -help` 看全部）：`-duration`，`-seed`；价格路径 `-crash-at -crash-for -crash-pct -rebound -volatility`；市场 `-pool-weth -spot-oracle -exchange-depth`；人群 `-borrowers -ltv-min -ltv-max -noise -liquidators -no-arb -llm -llm-mix`；网络 `-miners -hashrate -delay -jitter -drop -partition-at -partition-for -confirmations`。

运行结束时打印的报告里，每个 Agent 有 `pnl`（盈亏，按最终的交易所价格计价）、`hold-pnl`（什么都不做、拿着初始资产的盈亏）和 `alpha = pnl − hold-pnl`。在一个下跌 30% 的市场里人人都亏钱，**alpha 才说明策略本身的好坏**。输出目录里的 `timeseries.csv`（每秒的价格、债务、坏账、重组次数）、`chain_events.csv`（从链上日志读出的**每一笔** swap、存取借还、清算、预言机更新，包括你的 Agent 的）、`events.json`（内置 Agent 自己记录的动作和决策）、`summary.json` 和你的 Agent 的日志（`agent-<名字>.log`、`.decisions.jsonl`）是做分析的原材料；`python3 pysdk/examples/plot_run.py results/run1` 画出一张总览图。

> 一次运行要启动 3 个节点进程和十几个 Agent，在笔记本上会占用几个 CPU 核心。仿真跑的是真实时间：60 秒的场景就是 60 秒，外加半分钟左右的部署和收尾。不加 `-out` 时结果写到 `results/run-<日期>-<时间>/`。

### 3.3 任务 2.1：热身（6 分）

在报告里简要回答（每题几句话、一张图或一段命令输出即可）：

1. **你的链能跑合约。** 用 web3.py、ethers.js 或 Foundry 在你的 devnet 上部署一个 ERC-20 代币（可以就用 `contracts/Token.sol`，或者自己写一个），铸币、转账，并读出 `Transfer` 事件。`pysdk/examples/basics.py` 是现成的起点。
2. **看懂一次仿真。** 跑一次默认场景，用 `plot_run.py` 画出交易所、预言机、AMM 三条价格曲线（默认情况下借贷市场用的就是预言机价格；加 `-spot-oracle` 时它用 AMM 价格，图里会多一条）。解释：AMM 价格为什么会跟着交易所价格走？预言机为什么滞后？清算发生在什么时候，为什么是那几个借款人？
3. **AMM 的成本。** 在 500 WETH / 1,000,000 USD 的池子里卖出 20 WETH 能拿到多少 USD？比按 2000 的价格少了多少，其中多少是手续费、多少是价格冲击？卖 100 WETH 呢？先用 DEFI.md 里的公式算，再在链上验证：`go run ./cmd/sim -noise 0 -no-arb -borrowers 0 -crash-at 0 -volatility 0 -agent-weth 150 -agent "me=python3 你的脚本.py"` 里没有别人动池子，你的脚本用 `w.reserves()` 和 `w.sell_weth(20)` 就能比较公式和实际成交。
4. **亲眼看到一次重组。** 用 `go run ./cmd/devnet -easy -mine=false` 启动（`-easy`：难度很小、几乎不变，手动出块立即完成，每个块的分量都差不多），在控制台里依次操作：
   1. `partition n1 n2,n3`；
   2. 在另一个终端向 n1 发一笔转账，例如 `cast send <bob 的地址> --value 1ether --private-key <alice 的私钥> --rpc-url http://127.0.0.1:28001 --async`（`--async` 让它立即返回交易哈希，不等回执）；
   3. `mine n1 1`，用 `cast receipt <交易哈希> --rpc-url http://127.0.0.1:28001` 确认交易在 n1 的 1 号块里；
   4. `mine n2 2`，然后 `status`：比较两边链头的总难度，预测愈合后谁会赢；
   5. `heal`，等一两秒，再查 n1 上的回执；
   6. `mine n2 1`，再查一次。

   每一步之后发生了什么？用 `reorgs n1`、`chain n1` 和节点日志解释整个过程。如果有一个交易者在第 3 步看到回执就把它当作"成交"，会有什么后果？（为什么要 `-easy`：默认难度会随时间下调，几秒内挖出的一个块可能比几十秒后挖出的两个块更重。想一想这又说明了什么。）

### 3.4 任务 2.2：你的第一个交易 Agent（12 分）

写两个 Agent，在同一个市场里比较它们：

- **一个规则 Agent**：可以从 `pysdk/examples/momentum.py`（趋势跟踪）出发，也可以自己设计（AMM 与交易所之间的套利、均值回归、自动去杠杆的杠杆多头……）。它是你的基线。
- **一个 LLM Agent**：从 `pysdk/examples/llm_trader.py` 出发。它的结构是"观察 → 构造提示词 → 模型给出 JSON 计划 → **代码校验** → 执行 → 记住结果"。你至少要改进它的观察（让模型看到什么）、提示词和校验层，并说明理由。

在默认的暴跌场景和一个 V 形场景（`-rebound 0.2`）下评估，每个场景**至少 3 个随机种子**（`-seed`）。`pysdk/examples/sweep.py` 演示了怎样批量跑、怎样汇总。报告中需要：

- 两个 Agent 的设计：观察什么，能做哪些动作，提示词的结构，校验和风控规则。
- 结果：pnl、alpha（相对于持有不动）、被清算次数、交易次数，LLM 的调用次数与平均延迟；给出均值和跨种子的波动范围，与内置机器人放在一起比较。
- 至少 3 个具体的 LLM 决策案例（`agent-名字.decisions.jsonl` 里有每一次的输入摘要、计划、执行结果）：一个做得好的，一个做得差的，一个被你的校验层拦下或修改的。模型为什么那样决定？

几条必须遵守的原则：

- **模型提议，代码决定。** 模型的输出是不可信的输入：动作类型、金额都要检查，超出余额或风险上限的要截断或拒绝。
- **私钥和 API key 永远不进提示词**，也不要写进代码或提交到 Git（用环境变量或 `LLM_API_KEY_FILE`，见 AGENTS.md）。
- 从链上读到的任何文字（代币名称、事件）都是**数据**，不是指令。
- 这个任务看的不是你赚了多少钱（暴跌里跑赢持有很难），而是 Agent 是否可靠，以及你的评估是否公平、诚实。

### 3.5 任务 2.3：研究课题（22 分）

从下面选**一个**课题（或者自拟），提出一个可以用数据回答的问题，设计实验，回答它。每个课题给了一个出发点；具体问什么、怎么测，由你决定。

**A. 羊群效应与信息瀑布。** 几个 LLM Agent 都能看到公开的成交记录时（内置 LLM 交易者用 `-llm-tape`；你自己的 Agent 用 SDK 的 `w.recent_trades()` 读链上的成交），会不会朝同一个方向交易，放大暴跌？人设相同和人设各异时有什么区别？可以用 LSV 羊群度量（Lakonishok, Shleifer & Vishny, 1992）或"同向决策比例"来量化，并与没有 LLM 的对照组比较交易所价格的跌幅。

**B. 预言机设计与清算连锁。** 借贷市场用 AMM 即时价格做预言机（`-spot-oracle`）时，池子深度（`-pool-weth`）和交易所深度（`-exchange-depth`，让链上抛售能传导到交易所价格）怎样影响清算次数和坏账？（`summary.json` 的清算统计和 `chain_events.csv` 都来自链上日志，你的攻击者 Agent 做的清算也包括在内。）进一步：写一个攻击者 Agent，通过操纵即时价格触发清算并从中获利；再设计一个防御（例如 TWAP 时间加权价格，写成新的预言机合约），用实验证明它有效。

**C. 重组风险与确认数。** 在高延迟的网络里（`-delay`、`-jitter`、`-partition-at`）分叉和重组很频繁。一个看到回执就认为"成交"的 Agent 会在多大比例上判断错误？这个比例随它等待的确认数（`-confirmations`，或你自己的 Agent 里的逻辑）怎样变化？写一个通过确认数和 `removed: true` 的日志事件来跟踪"真实持仓"的 Agent，量化延迟与安全之间的取舍。

**D. 51% 攻击与双花。** 给一个矿工远超其他人的算力（`-hashrate`），让它秘密地挖一条不包含自己付款交易的分叉，等"商家" Agent 在 k 个确认后发货，再公布这条分叉。攻击成功率怎样随算力占比和 k 变化？与比特币白皮书（Nakamoto, 2008）第 11 节的概率公式对比。（需要修改矿工，见 Part 3 的说明。）

**E. 自私挖矿。** 实现 Eyal & Sirer（2014）的自私挖矿策略：挖到块先不公布，择机放出。测量自私矿工的收益占比与算力占比的关系，找出它开始有利可图的门槛，并和论文的理论曲线对比。

**F. MEV：抢跑与三明治攻击。** 矿工按小费从高到低打包交易，而待打包的交易对所有人可见（`txpool_content`，SDK 的 `w.pending_txs()`）。写一个 Agent 监视交易池里的大额 swap，用更高的小费在它前面买、更低的小费在它后面卖（SDK 的交易函数都有 `tip_gwei` 和 `wait=False` 参数）。受害者损失多少？哪些防御有效（更小的滑点容忍度、拆单、提交-揭示）？

**G. 链上提示词注入。** 链上的文字任何人都能写：部署一个名字里藏着"指令"的代币，或者在交易数据、事件里写入文本。如果 Agent 把这些内容放进提示词，能被诱导做出有害的交易吗？不同模型、不同的提示词结构的易感性如何？设计并评估防御（数据与指令分离、结构化输入、输出校验、权限最小化）。**只在你自己的本地网络上做。**

**H. 模型与提示策略。** 比较不同规模或类型的模型（以及推理模式、思维链、反思、更长的历史、工具调用），在同样的市场里的表现、决策延迟和成本。控制变量、重复实验，并报告每次运行的 API 费用。

**I. 做市商的经济学。** 写一个在 AMM 中添加和撤出流动性的 LP Agent（合约已支持 `addLiquidity`/`removeLiquidity`），测量无常损失与手续费收入。在什么波动率、什么价格路径下提供流动性划算？

**J. 自选。** 新的 DeFi 协议（稳定币、预测市场、拍卖）、多 Agent 的协作或对抗、对 PoW 机制本身的实验……任何有趣的想法。

**实验方法上的要求**（无论选哪个课题）：

- 先写下问题和**假设**，再做实验；设计**对照组**（没有 LLM、规则 Agent、持有不动、修复前/修复后）。
- 每个条件**至少 3 个种子**，报告均值和离散程度；条件多时考虑置信区间或显著性检验。一次运行的结果不能说明任何问题：出块时刻、交易排序、LLM 的输出每次都不一样。
- 一次只改一个变量；记录每次运行的完整参数（`summary.json` 里有），保证别人能复现。
- 如实报告不符合预期的结果，并尝试解释。**一个设计严谨、结论是"没有效应"的实验，和一个发现了显著效应的实验得分相同。**
- 控制成本：先用 `mockllm` 把整个流程跑通，再用真实模型；报告总的调用次数和费用。

## 六、常见问题

**Q：节点不出块？**
看日志。还有 `TODO: ... is not implemented yet` 说明 Part 1 没写完。`miner started` 之后什么都没有：可能是自动挖矿被关了（`status` 看 mining 一列），或者你的 `mine` 一直返回错误（在 `loop` 里把错误打印出来）。

**Q：有时候十几秒都不出一个块，是不是我的代码慢？**
不一定。PoW 的出块间隔服从指数分布：平均 2.5 秒时，超过 10 秒的间隔大约每 50 个块出现一次。用 `chain n1 50` 看一段时间里的平均间隔，比盯着一个间隔更有意义。

**Q：两个节点停在同一高度、不同哈希，不再变化了？**
如果它们的总难度相同，这是**正确的**：平局时各自保留先看到的块，直到有人挖出下一个块打破平局。`mine n1 1` 之后它们应该一致。如果总难度不同还不收敛，那是同步有问题（任务 7）。

**Q：`TestExecStateRootVector` 失败？**
它先检查四个账户的余额（矿工 = 出块奖励 + 全部手续费），再检查状态根。余额不对时，看提示里是谁的余额、差多少（差 2 ETH 是奖励，差几万 gwei 是手续费）。余额都对而状态根不对，说明状态里还有别的不同（nonce、多出来的账户）：确认你只通过 `applyTx` 和 `payReward` 改动状态，每笔交易恰好执行一次。

**Q：测试报 "did not return within ...: a deadlock?"**
通常是在 `insertBlock` 里调用了 `InsertBlock`/`InsertChain`（`insertMu` 已经被持有），或者交易池的锁没有释放、在持有锁时又去拿同一把锁（Go 的 `sync.Mutex` 不可重入），或者一个没有接收者的 channel 在等待。用 `go test -timeout 60s` 运行，超时时 Go 会打印所有 goroutine 的调用栈，看它们卡在哪里。

**Q：交易发出去了，一直没有回执？**
依次检查：链在出块吗？发送方有足够的 ETH 付手续费吗？nonce 有没有跳号（前面的交易没进来，后面的就会一直排队）？`curl -s -X POST localhost:28001 -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"txpool_content","params":[]}'` 能看到交易池里在等什么。

**Q：MetaMask 报 nonce 不对？**
devnet 每次重启都是一条新链，MetaMask 还记得旧链上的 nonce。在 MetaMask 的"设置 → 高级 → 清除活动和 nonce 数据"里重置账户。

**Q：LLM 太贵 / 太慢 / 没有 key？**
调试阶段一律用 `go run ./cmd/mockllm`，它离线、免费、即时返回格式正确的随机决策（偶尔故意返回非法 JSON，测试你的错误处理）。正式实验用便宜的模型，决策间隔设长一些（`llm_trader.py --every 15`），先跑一次估算费用。本地也可以用 Ollama（AGENTS.md 有配置方法）。

**Q：LLM Agent 的每次决策都报错或超时？**
先运行 `python3 pysdk/examples/llm_check.py`。共享的模型服务没人用时会缩容，第一次请求可能要等 5–10 分钟；等它几秒内就能返回，再开始仿真。返回空回答通常是推理模型把 token 都用在了"思考"上：SDK 默认关闭思考，如果你开了（`LLM_THINKING=on`），决策间隔要放到一分钟以上（AGENTS.md §7）。

**Q：同样的 `-seed`，两次结果不一样？**
种子只固定了交易所价格的路径和脚本机器人的随机性。出块时刻、交易的打包顺序、LLM 的回答每次都不同，所以必须多次重复、看统计量。

**Q：我发现框架有 bug？**
请带着复现步骤联系助教。

**Q：Windows 上 `-agent "me=python3 ..."` 报找不到 python3？**
仿真器在 Windows 上用 `cmd /C` 启动你的命令，Python 通常叫 `python`：写成 `-agent "me=python pysdk/examples/momentum.py"`。

**Q：Part 2 可以用 Go 以外的语言吗？**
可以。仿真器通过环境变量把节点地址、私钥和合约地址交给你的程序，用什么语言都行（AGENTS.md 有接口说明）；只是 Python 和 Go 有现成的 SDK。建议用 Go。
