# DeFi 入门：本实验用到的概念

本文用本实验的合约（`contracts/`）讲清楚 Part 2 需要的 DeFi 知识。所有数字都可以在你的 devnet 上验证。

## 1. 账户、代币与授权

链上有两种账户：**外部账户**（由私钥控制，能发交易）和**合约账户**（由代码控制，只能被调用）。ETH 是链的原生货币，用来付手续费（gas）；其他"币"都是合约里的记账。

**ERC-20** 是代币合约的标准接口：`balanceOf(地址)`、`transfer(收款人, 数量)`、`approve(花费者, 额度)`、`transferFrom(付款人, 收款人, 数量)`。代币数量是整数，带 18 位小数：1 USD 在链上是 `10^18`。

**授权（approve）** 是 DeFi 的基本动作：你要让 AMM 从你的账户里拿走 USD，得先 `usd.approve(amm, 额度)`，然后 AMM 在 `swap` 里调用 `usd.transferFrom(你, amm, 数量)`。所以每个 Agent 开始时都要先授权（SDK 的 `approve_all()`）。无限额度（`2^256 − 1`）很方便，但也意味着被授权的合约有漏洞时你的余额全部暴露，真实世界里要谨慎。

**交易的成本**：`gasUsed × gasPrice`。本链基础费用为 0，gasPrice 就是你出的小费，全部给矿工。一次转账约 2.1 万 gas，一次 swap 约 7–10 万 gas。小费越高，矿工越优先打包（这一点在 §6 MEV 里很重要）。

## 2. AMM：自动做市商

传统交易所用订单簿撮合买卖。**AMM** 用一个资金池和一个公式代替：池子里有 `x` 个 WETH 和 `y` 个 USD，交易必须保持 `x · y = k` 不变（Uniswap V2，本实验的 `AMM.sol`）。

**价格**：池子的即时价格是 `y / x`（USD/WETH）。初始 500 WETH / 1,000,000 USD，价格 2000。

**卖出 Δx 个 WETH 能拿到多少 USD**（先扣 0.3% 手续费）：

```
Δx' = Δx × 0.997
Δy  = y × Δx' / (x + Δx')
```

例：卖 10 WETH，`Δx' = 9.97`，`Δy = 1,000,000 × 9.97 / 509.97 ≈ 19,550 USD`，均价约 1955，比 2000 少约 2.3%：其中 0.3% 是手续费，其余是**价格冲击**（你自己的交易把价格推低了）。卖得越多冲击越大：卖 50 WETH 均价约 1813。卖出之后池子价格变成 `(y − Δy)/(x + Δx)`，约 1922。

**套利让价格跟着市场走**：池子价格低于外部市场时，套利者在池子里买、在外面卖，直到价差小于手续费加冲击。所以 AMM 的价格总是略微滞后于真实价格，并在大单之后短暂偏离。

**滑点保护**：`swap(tokenIn, amountIn, minAmountOut)` 在实际得到的少于 `minAmountOut` 时回滚（`"slippage"`）。从你看到报价到交易被打包之间，别人可能已经交易了：不设滑点保护就可能被"三明治"（§6）。

**流动性提供者（LP）**：`addLiquidity` 按当前比例存入两种代币，获得份额；`removeLiquidity` 取回。LP 赚手续费，但价格变动时会有**无常损失**：价格从 p 变到 p·r，LP 的资产价值是持有不动的 `2√r/(1+r)` 倍（不含手续费）；价格翻倍或减半时约损失 5.7%。

## 3. 借贷与清算

`Lending.sol` 是一个简化的 Aave/Compound：存入 WETH 作为抵押品，借出 USD。

| 参数 | 值 | 含义 |
|---|---|---|
| LTV | 75% | 最多能借抵押品价值的 75% |
| 清算阈值 | 80% | 债务超过抵押品价值的 80% 时可以被清算 |
| 清算奖励 | 5% | 清算人拿走的抵押品多 5% |
| 清算比例 | 50% | 一次最多代还一半债务 |
| 利率 | 每秒 1e-6（仿真的默认值） | 债务随区块时间戳增长；几分钟的仿真里利息很小 |

**健康因子** `HF = 抵押品价值 × 80% / 债务`，小于 1 就可以被清算。抵押品价值用**预言机**的价格计算。

例：存 10 WETH（价格 2000，价值 20,000），借 14,000 USD（LTV 70%），HF = 16,000/14,000 ≈ 1.14。价格跌到 1750 时 HF = 1.0；跌到 1500 时，任何人都可以代还 7,000 USD，拿走 `7,000 × 1.05 / 1500 = 4.9` WETH（价值 7,350）：借款人损失了 350 USD 的清算罚金。

**为什么有人愿意清算**：因为有利可图（5% 奖励）。清算人拿到 WETH 后通常立刻卖掉换回 USD，这就产生了下一节的问题。

**坏账**：价格跌得太快、清算来不及时，抵押品价值可能低于债务，差额就是协议的坏账（`summary.json` 里的 `badDebtEnd` 和 `badDebtMax`，`timeseries.csv` 的 `bad_debt` 列）。

## 4. 预言机

借贷合约自己不知道 WETH 值多少钱，要问预言机。本实验有两种：

- **FeedOracle**：一个报价人（Reporter）每秒把交易所价格写到链上，像 Chainlink 的简化版。它可信但**滞后**：报价交易要等打包，市场急跌时链上价格落后于真实价格（`maxOracleLagPct`），清算也随之延迟。
- **AMMOracle**：直接读 AMM 池子的即时价格。它实时、不需要报价人，但**可以被操纵**：一笔大额卖单就能瞬间压低池子价格，触发本不该发生的清算，攻击者再低价买回。这类预言机操纵是 DeFi 历史上损失最大的攻击类型之一。防御方法包括时间加权平均价格（TWAP）、多数据源、价格变动上限。

`-spot-oracle` 让借贷市场使用 AMMOracle。

## 5. 清算连锁

```
价格下跌 → 一些仓位 HF < 1 → 被清算 → 清算人把 WETH 卖进 AMM → AMM 价格进一步下跌
    ↑                                                                    │
    └──── （spot 预言机：直接）/（feed 预言机：通过套利者传导到交易所） ←─────┘
```

用 spot 预言机时这个循环是直接的。用 feed 预言机时，链上的抛售要先通过套利者传到交易所（套利者在池子里低价买入、在交易所对冲卖出），交易所价格才会下跌：`-exchange-depth` 设定交易所有多深，越浅传导越强。借款人的杠杆越集中在相近的清算价位，连锁越剧烈。

## 6. MEV：交易顺序的价值

矿工决定一个块里有哪些交易、按什么顺序（本实验的矿工按小费从高到低）。待打包的交易在交易池里对所有人可见（`txpool_content`）。于是：

- **抢跑（front-running）**：看到一笔大额买单，抢先用更高的小费买入，等它把价格推高后卖出。
- **三明治攻击**：在受害者的 swap 前面买（高小费）、后面卖（低小费），受害者以更差的价格成交，攻击者赚取差价。受害者的滑点容忍度越大，可被榨取的越多。
- **清算竞争**：多个清算人争抢同一个仓位，小费越高越可能抢到。

这些可提取的价值叫 **MEV**（Maximal Extractable Value）。矿工自己也可以做这些事，甚至为了 MEV 重组链。

## 7. 终局性与确认数

PoW 链上，一笔交易出现在区块里不代表它最终生效：如果另一个分支变得更重，这个区块会被撤销（Part 1 的链重组）。交易上面压的块（**确认数**）越多，被撤销的概率越低。比特币白皮书第 11 节给出了攻击者算力占比 q 时、追上 k 个确认的概率，它随 k 指数下降，但只要 q > 0 就永远不是零；q ≥ 50% 时攻击者必然成功（"51% 攻击"）。

对 Agent 的影响：

- 看到回执就认为"成交了"的 Agent，在重组时会对自己的持仓产生错误判断。
- 日志过滤器会把被撤销区块里的事件以 `removed: true` 再报告一次，处理事件的 Agent 必须能撤销它们。
- 等待确认更安全，但更慢：市场在你等待的时候继续变化。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| gas / 小费（tip） | 交易消耗的计算量 / 每单位 gas 付给矿工的价格 |
| nonce | 账户的交易序号；也指 PoW 中矿工尝试的数字（两者无关） |
| 回执（receipt） | 交易执行的结果：成功或回滚、消耗的 gas、产生的事件 |
| 事件 / 日志（event / log） | 合约执行时写下的记录，如 `Transfer`、`Swap`、`Liquidate` |
| 回滚（revert） | 合约拒绝执行（`require` 失败），状态不变，但 gas 照付 |
| 滑点（slippage） | 实际成交价与预期价格的差 |
| LTV / 健康因子 | 债务与抵押品价值之比 / 距离被清算还有多远 |
| 规范链 / 重组 / 确认数 | 见 Part 1 和 SPEC.md |
